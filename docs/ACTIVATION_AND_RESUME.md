# Model 0.19：选择、启用与下次接续

## 1. 已实现的统一流程

网页现在有“选择模型，启用并接续”面板。现有模型卡片统一进入这一入口，不需要用户识别后端或把 Notebook 代码复制进网页。

选择来自已授权 Drive API 或 Drive Desktop 扫描结果的模型后，Runtime 计算：来源与文件版本、模型家族、固定适配器、当前RAM/VRAM/磁盘、依赖与缓存情况。参数可按模型保存。支持的任务可以一次准备，也可以准备后执行；首次会准备固定后端、校验并读取所需权重。未知模型会给出缺少适配器的原因，不显示虚假的成功。

“只准备，下次复用”仅意味着文件/环境准备通过，不意味着已经做过一次真实模型生成。响应里的 `model_execution_verified` 仍为 false。真实执行产生的结果有单独记录。

## 2. 接续究竟保存什么

默认本地根目录是 `D:\Model`。

| 对象 | 保存位置/方式 | 重新启动时的行为 |
|---|---|---|
| 模型文件 | Drive/API或桌面来源的缓存，完成文件保留 | 校验身份和完成证据后复用 |
| 下载中的文件 | 身份绑定的 `.part` | 同一文件版本可续传；无可靠来源校验时宁可重下未完成文件 |
| 批量任务 | `activation/lifecycle.sqlite3`，SQLite WAL/FULL | 标记中断状态，等待用户点接续 |
| 完成结果 | `activation/jobs/<id>/<step>/`及结果收据 | 校验SHA256后跳过已完成项 |
| 提示词/参数/输入图 | 本地任务记录、工作区快照 | 恢复任务原始输入；无需为该任务重新上传图片 |
| 聊天历史 | 同一本地数据库中的按来源、模型、版本隔离记录 | 重启相同模型后恢复；模型版本改变不会串用 |
| OAuth令牌 | 只存在当前进程内存 | 不持久化；重新授权后才能访问来源 |
| GPU/RAM中的驻留模型 | 不持久化 | 新进程需要重新加载权重，不等于重新联网下载 |

**接续粒度是任务项。** 例如10张中4张完成、第5张中断，下次保留前4张，重跑第5张及后续项。不是从第5张第7个扩散步接着计算。任务结果保存成功、但数据库提交前崩溃的窗口，恢复时利用收据补写进度，不重复生成这张。

未产出可靠完成收据时，单项会重跑。外部ComfyUI进程在主Runtime崩溃后可能仍运行：本轮没有完成所有孤儿推理任务的远端核销协议，所以不承诺每次物理推理恰好一次。已确认的结果不会因继续任务被覆盖或删除。

## 3. 不再仅凭“下载完成”标记认定模型可用

对分片包先读取有界JSON索引，逐一查找 `weight_map` 所引用文件，再开始大文件准备。完整性验证检查文件大小、非空、safetensors头部和偏移/长度、路径安全及大小写冲突；缺一个分片就停止并报告具体路径。

Drive提供MD5时，缓存落盘前比较MD5并记录本地SHA256；从官方模型站点准备量化副本时，固定仓库提交、文件大小和提供方SHA256。已完成缓存有版本、大小、校验及文件mtime证据；旧缓存有可比对的MD5时允许本地升级校验，不强迫重新下载。部分文件不会因只是“同名同大小”而直接当作正确文件。

**结构校验不是张量内容的密码学全量验证，也不是模型推理验证。** 没有可信提供方哈希的文件会保留这个证据缺口；不会在报告中写成来源哈希已校验。

## 4. 本轮接入范围

| 模型或任务 | 运行路径 | 本轮证据与限制 |
|---|---|---|
| 有明确聊天类别的单个GGUF | 现有llama.cpp聊天 | 统一启动/参数/历史接续代码与模拟HTTP测试；继承0.18历史CPU证据，未复测用户模型 |
| Qwen3 Embedding / Reranker | 既有独立任务服务 | 统一任务输入与持久结果，不将大向量截断成只有预览 |
| GOT-OCR、Chronos-2、TimesFM | 私有Python原生工作器 | 原有适配器接入统一任务链；历史真实CPU证据不冒充本轮实测 |
| Pony、原有Qwen-Image2.1和FLUX2 FP8 | 现有固定ComfyUI图 | 保留原工作流和条件；不把文生图入口冒充任意图像编辑 |
| FLUX.2 klein4B完整Diffusers包 | 新专用分阶段工作器 | 1–3张参考图、4步蒸馏、先编码再卸载文本模型；仅接受4B蒸馏配置；实际GPU待验收 |
| Qwen-Image-Edit-2511 | 新GGUF Q4_K_M固定工作流 | 必须显式选择另存量化副本；原始BF16文件不被替换；实际GPU待验收 |
| Wan / Hunyuan既有视频 | 已登记ComfyUI / Native工作流 | 硬件不够就阻止；本轮不承诺8GB显存能跑大视频模型 |
| 其他任意模型 | 明确“缺适配器” | 未完成，不自动猜类、不自动执行远端代码 |

Qwen2511运行副本来自登记的三个仓库/文件：Unsloth Q4_K_M主模型、Comfy-Org的Qwen2.5VL FP8编码器、Qwen VAE。网页必须勾选同意后才下载权重。首次仅获取公开元数据以计算大小和绑定版本，不会因此下载整个原始模型。运行副本留在D盘；原先Drive约57GB模型属于另一份原始资料。

硬件门槛是**规划的保守门槛，不是已测性能保证**。Qwen GGUF入口要求约7.5GB以上显存和22GiB当前可用RAM；8GB显存FLUX分阶段入口要求24GiB当前可用RAM。32GB机器开很多程序后可能达不到“当前可用”要求，页面会解释原因。大显存T4与本地8GB不能只按显卡名称互换方案。

## 5. 环境与后端准备

Native任务使用D盘的私有Python环境，固定torch/torchvision匹配组合，并在继续前检查原生nms算子与指定类导入。不会再次把Colab全局PyTorch与旁路torch混装。

新下载的ComfyUI-GGUF节点固定到提交 `6ea2651e7df66d7585f6ffee804b20e92fb38b8a`，ZIP先检查路径、链接、数量及体积；安装节点依赖时约束现有ComfyUI torch/torchvision版本，拒绝静默替换整套CUDA栈。已有用户节点不会因为本次版本登记就强制更新；节点能力仍在启动前核对。

剩余供应链验收：旧Managed ComfyUI Portable和私有Python引导部分没有全部转成离线、预登记文件SHA清单。下载使用指定官方HTTPS地址/版本；Windows源码启动器每次使用前校验Python EXE的PSF Authenticode签名。这里不能等同于整个依赖目录逐文件可信哈希锁定。

## 6. 页面操作

先退出旧托盘服务，完整解压候选包，双击 `Run-Model-0.19.cmd`。首次准备少量运行程序，不下载全部模型。选Drive Desktop时用原生目录选择器授权 `AI-Model-Vault`，不需要网页OAuth；API来源仍要登录和授权。

扫描后选模型，在统一面板检查可用性，填写任务输入。图片任务可填“批量额外指令”，每行一项、最多100项。点击运行后逐项保存。关闭浏览器不等于取消后台本机任务；关闭本机Runtime会停止控制服务。下次重开本机Runtime、重新扫描来源，历史里点击接续。

未登录、来源掉线、硬件不足、后端缺节点、校验失败不会假装运行成功。模型版本/内容/量化方案变了不能继续旧任务；应保留旧记录并新建任务。取消不会删除完整模型和已完成输出。

## 7. 验收边界

已验证的是本地源码、真实SQLite/文件系统/线程/HTTP与浏览器DOM交互，推理使用受控假工作器。未在用户Y9000P、真实DriveFS占位文件、真实NVIDIA生成、双机HTTPS、Windows新EXE上验证。未知模型家族仍需专用适配器。这是可接续候选，不是“所有模型全验收最终版”。
